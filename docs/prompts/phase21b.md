# Phase 21b: マスターボリュームとマスター設定(全アプリから届く装置の設定)

- 契約日: 2026-09-22
- 参照: `docs/results/phase21a.md`(直前の到達点。**特に試用所感 D-1〜D-5**)、
  `docs/results/phase21.md`(内蔵音源とミキサ)、`docs/hostapi.md` §7(audio)、
  `shared/hostapi_defs.h`(audio の契約)、`docs/design/ui-conventions.md`、
  `src/components/wasm_runtime/hostapi.cpp` / `screensaver.cpp` / `launcher.cpp`、
  `src/components/audio/audio.cpp`、`src/components/power_key/`、
  `hosts/linux/hostapi_sdl.c` / `main.c`
- 結果報告先: `docs/results/phase21b.md`

## 目的

**装置全体の音量を「アプリより上」に置き、どのアプリからでも変えられるようにする。**

Phase 21a でドラムを鳴らせるようになったが、**音量の持ち方が破綻している**:

- ドラムの粒を聞き分けるために **HW のボリュームつまみを最大にした**ところ、
  **他のアプリでは音が大きすぎる**(所感 D-4)。
- **ソフト側の音量はアプリのセッション状態**で、**アプリを切り替えるたびに 98 に戻る**
  (`hostapi_audio_reset()` が `Volume_adjustment(98)`)。**「マスター」になっていない。**
- **音量を変える UI がどこにも無い**(`hostapi_audio_set_volume` はあるが、mp3player の
  V− / V+ 以外に使われていない)。

本フェーズで **(1) 音量をホストが持つ装置の設定にし、(2) 既定値を適正な値(50% 前後)にし、
(3) どのアプリからも「マスター設定」に入れる**ようにする。

**所感 D-1(内蔵スピーカーで Kick が聞こえない)と D-3(音色ごとの音量バランス)は本フェーズに含めない。**
音量の土台を先に作る(そこが動くと音色の評価がやり直しになるため)。

## 決定済みのスコープ(2026-09-22 のユーザー回答)

- **まずマスターボリュームを作る。**
- **ソフトウェア上のボリュームの既定値を 50% 等、ちょうどいいところに設定する。**
- **各アプリから、マスターボリュームを含む「マスター設定」にアクセスできるようにする。**

## 前提(再調査不要。ただし着手時にソースで確認すること)

- **P1: 音量は今「アプリのセッション状態」である。**
  `hostapi_audio_reset()`(アプリの起動 / 停止で呼ばれる)が**両ホストとも音量を 98 に戻す**
  (実機 `hostapi.cpp` の `audio::Volume_adjustment(98)`、Linux `hostapi_sdl.c` の `s_master_vol = 98`)。
  **`shared/hostapi_defs.h` の audio の契約にも「マスター音量 … 曲をまたいで持続する」とあるが、
  アプリをまたぐ持続は書かれていない。** 本フェーズで**契約を変える**ことになる(ゲート 2)。
- **P2: 音量は MP3・クリック・内蔵音源のすべてに掛かる。**
  実機は `Mp3Player::volume_`(`write_fn` の MP3、`voice_start_tone` / `voice_start_drum` の
  発音時に焼き込む)、Linux は `s_master_vol`。**発音中の音には効かず、次の発音から効く**
  (既存の契約。変えない)。
- **P3: ホストがアプリの画面の上に描いた前例は `screensaver.cpp` だが、
  これは「メニュー表示中だけ」で、アプリ実行中は無効。**
  アプリの描画は `hostapi.cpp` が `s_screen`(`lv_obj_create(nullptr)` で作った画面)の上に
  `lv_label_create` / `lv_obj_create` で置いている。**アプリ実行中にホストが上に重ねる仕組みは
  まだ無い**(LVGL の `lv_layer_top()` 等を使うことになる)。
- **P4: 入力はホストのキューを経由する。** アプリは `hostapi_poll_event` で受け取るので、
  **ホストが配送を止めれば、アプリにタッチを渡さずに済む**(オーバーレイ表示中に必要)。
- **P5: HW キーの割り当ては埋まりつつある。**
  `power_key`: **短押し(≦500ms)= 戻る / 1000〜2000ms = 強制ホーム / 2000ms 以上 = 電源断**。
  Linux は **Backspace = 戻る / ESC = 強制終了**。**ダブルクリックは未使用。**
- **P6: 右上はアプリが使っている。** sequencer はヘッダ右(`HDR_STATUS_X = 200`〜320、y 0〜26)に
  **BPM / 再生位置**を出し、**長押し + 左右ドラッグで BPM を変える**。
  **所感 D-4 の「右上にアイコン」をそのまま実装すると、ここと衝突する。**
- **P7: 設定の保存先は用意がある。** Phase 20 で `hostapi_fs_read` / `fs_write` を足し、
  データルートは**実機 `/sdcard/data` / Linux `./sdcard/data`**。
  **ホスト自身がここに設定ファイルを置くことはまだしていない。**
  なお Phase 20 は**アプリのデータ**について「起動時の自動ロードはしない」と決めたが、
  **装置の設定は別の判断**でよい(ステップ 0 で決める)。
- **P8: 回帰への影響。** `scripts/device-regress.sh` は heap と警告しか見ないので、
  音量の既定値が変わっても**合否は変わらない**。ただし**オーバーレイの表示中に
  `app_tick` が止まる / イベントが溜まる**ような作りにすると回帰に出る可能性がある。
- **P9: mp3player は音量 UI を持っている**(V− / V+ が `hostapi_audio_set_volume` を呼ぶ)。
  **マスターに変えると意味が重なる**ので、扱いを決めること(ステップ 0-e)。
  **既存 5 本の `.wasm` は再ビルドしない**のが原則(ゲート 4)。

## ゲート(必須)

1. **ステップ 0(設計メモ)の報告 → 承認**を経てから実装に入る。
2. **`hostapi_audio_set_volume` の意味を変える(アプリをまたいで持続する)のは契約変更**なので、
   `shared/hostapi_defs.h` と `docs/hostapi.md` の文面を設計メモで示し、**承認を得てから**実装する。
   **シグネチャは変えない。**
3. **Host API の関数を増やすときは承認ゲート**(本フェーズでは**増やさずに済む可能性が高い** — P4 のとおり
   ホスト側だけで完結する見込み)。
4. **既存 5 本の `.wasm` を再ビルドしない**(回帰の基準)。**sequencer も、必要が無ければ触らない。**
5. **実機 WAMR プールの余裕が 2KB を切ったら報告して止まる**(現在 **112,424 / 130,880 = 残り 18,456 B**)。
   本フェーズはホスト側が中心なので**プールは動かない見込み**。動いたら理由を書くこと。
6. `scripts/` / `docs/workflow.md` / `CLAUDE.md` の変更は提案 → 承認。
7. **一時コードは入れた直後にも `git diff` で確認する**(Phase 19 / 21 の教訓)。

#### ステップ 0: 設計メモ(実装なし・承認ゲート)

`docs/results/phase21b.md` のステップ 0 節に、次をすべて書く。

- **a. 音量を誰が持つか(契約変更の本体)**
  - **ホストが持ち、アプリをまたいで持続する**ことを明記する。
    `hostapi_audio_reset()` から**音量のリセットを外す**(P1)。
  - **アプリが `hostapi_audio_set_volume` を呼んだときどうするか。**
    選択肢: (i) **そのままマスターを動かす**(mp3player の V− / V+ がマスターを変える)、
    (ii) **アプリごとのゲインを別に持ち、マスターと掛け算する**(2 段)、
    (iii) **アプリからの変更を無視する**(既存アプリの V− / V+ が効かなくなる)。
    **推奨は (i)**(語彙も挙動も増やさない。mp3player はそのまま使える)。**根拠を書くこと。**
  - **既定値**をいくつにするか(**50% 前後**)。**現在の 98 との差がどれだけ聞こえるか**を、
    **実機で確かめてから決める**(下記 0-f)。**HW のつまみは最大のまま**を前提にする。
  - **`shared/hostapi_defs.h` と `docs/hostapi.md` の文面**(差分をそのまま書く)。
- **b. マスター設定の入口(承認の本体。ここがいちばん悩ましい)**
  - **どのアプリからも届く**必要がある(P6 のとおり「右上にアイコン」は sequencer と衝突する)。
    次を比較して選ぶこと:

    | 案 | 入口 | 長所 | 短所 |
    |---|---|---|---|
    | **A** | **HW キーのダブルクリック**(短押し 2 回。P5 のとおり未使用) | **ABI もアプリも一切変えない。** 全アプリに自動で効く | **気づきにくい**(画面に手がかりが無い) |
    | **B** | **ホストが画面の隅に小さなアイコンを常時描く** + その領域をホストが食う | 見えるので分かる | **アプリの画面と衝突する**(sequencer のヘッダ右)。**「この領域はホストのもの」という規約**を新設し、**sequencer の画面を動かす**ことになる |
    | **C** | **画面の端からのスワイプ**をホストが横取り | 領域を専有しない | **入力の経路に手が入る**(アプリへ配送する前に判定する)。誤爆しやすい |
    | **D** | **ランチャー(メニュー)にだけ置く** | いちばん簡単 | **「各アプリから」を満たさない**(演奏中に音量を変えられない) |

  - **推奨は A + D の併用**(**HW キーのダブルクリックで、どこからでも開く**。
    加えて**メニューにも行を置いて見つけられるようにする**)。**この案でよいか承認を仰ぐ。**
  - **開いている間のふるまい**: `app_tick` は回すか止めるか、**タッチをアプリに渡さない**方法(P4)、
    **再生中の音はどうなるか**(**止めない**のが前提)、**閉じ方**(同じキー / 画面の外)。
  - **実機と Linux で同じ操作にすること**(Linux は Backspace のダブルクリック等)。
- **c. マスター設定の画面(ホストが描く)**
  - **v1 は音量 1 項目**でよい。ただし**後から項目が増える形**にする
    (スクリーンセーバーの時間、MIDI の設定 など)。
  - **描き方**: `screensaver.cpp` と同じ LVGL の直書き(`hostapi_draw_*` は**使わない** —
    あれはアプリのためのスロットで、ホストが使うと衝突する)。**アプリの描画スロットを
    1 つも消費しない**こと。
  - **操作**: 音量の上げ下げをどうするか(± ボタン / スライダー / ドラッグ)。
    **`docs/design/ui-conventions.md` の語彙に従う**(専用ボタンを置いてよい条件は §2 にある)。
  - **今の値の見せ方**(数値 / バー)。**0〜100 のまま**でよいか。
- **d. 保存(電源を切っても残るか)**
  - **残すべきか**を決める。**推奨: 残す**(装置の設定なので)。
  - 残すなら**どこに何を書くか**(P7。**ホストがデータルートに小さなファイルを置く**。
    形式・マジック・版番号。**アプリの `MBBK` とは別物**であることを明記)。
  - **起動時に読むか**(Phase 20 は「アプリのデータは自動ロードしない」と決めたが、
    **装置の設定は起動時に読むのが自然**。**回帰の初期状態が SD に依存しないか**を確認すること)。
  - **SD が無い / 壊れているときの既定値**。

  - **mp3player の V− / V+** をどうするか(P9。推奨は 0-a (i) でそのまま)。

## 追記(スコープ変更)

### 2026-09-22: ミキサー(ポート単位の音量)を追加する

実機の試聴でユーザーが出した結論:

> 操作感は非常に良いです。一方で、ボリュームについては、**Drum Machine は 50 くらい、
> mp3 player は 18 くらい**がちょうどよいと感じました。**マスターは 50 で良いですが、
> ミキサーで個別の音量を可変にはできますか?**

**できるので本フェーズに含める。** マスターが 50 で確定したので、当初「マスターが決まってから」
として外していた**ミキサー(所感 D-3)のうち、ポート単位のぶんを前倒しする。**

- **チャンネルは「ポート単位」**: **MP3 / 内蔵音源(ドラム)/ クリック**の 3 つ。
  **アーキテクチャのポート抽象(`architecture.md` §7)とそろう**うえ、
  今回の「MP3 だけ大きすぎる」を直接解く。
- **実効音量 = マスター × チャンネル**(どちらも 0..100)。
  既定は **マスター 50 / MP3 35 / ドラム 100 / クリック 100**
  (MP3 の実効は 50 × 0.35 = 17.5 ≒ ユーザーの言う 18)。
- **マスター設定の帯に 3 行足す**(項目が増えたら帯が伸びる、という 0-c の想定どおり)。
- **音色ごとのバランス(Kick / Snare / HH / Crash)は引き続き含めない。**
  音色そのものを作り直す次フェーズ(所感 D-1)で一緒に扱う
  — **音色が変わればバランスも取り直しになる**ため。
- **保存は引き続きしない**(U-24)。**チャンネルが増えたぶん、保存の価値は上がった**ので、
  その旨を残課題に書く。
